# Переход из инженера НТ в SRE — дорожная карта и самооценка

Документ помогает инженеру нагрузочного тестирования (НТ) оценить свои навыки
относительно роли SRE и выстроить маршрут перехода. Цель — **не «максимум везде»**,
а опереться на сильную базу НТ (Gatling, Jenkins, Grafana, Python) и добрать
недостающие треки.

> Есть интерактивная версия этой карты (с сохранением оценок и авто-подсчётом
> готовности) — канвас `lt-to-sre-roadmap`. Этот markdown — «бумажная» версия
> с расширенными примерами задач и инструментов для самооценки и печати.

---

## Как пользоваться

1. Прочитайте **шкалу уровней 0–4** и общие поведенческие якоря.
2. Для каждого навыка в матрице посмотрите **инструменты** и **примеры прикладных
   задач**. Правило: *если перечисленные задачи вы делаете самостоятельно и
   уверенно — ставьте себе балл ≥ целевого; если только «по инструкции» — на балл
   ниже*.
3. Проставьте свой балл в колонку **«Моя оценка»**.
4. Посчитайте готовность по трекам (шаблон в конце) и выберите 3–5 приоритетов роста.

---

## Шкала уровней 0–4

| Балл | Название   | Поведенческий якорь (что верно про вас) |
|:---:|------------|------------------------------------------|
| **0** | Нет опыта   | Не сталкивался, не владею терминологией. |
| **1** | Осведомлён  | Понимаю базовые понятия, повторяю действия **по инструкции под присмотром**. |
| **2** | Практик     | **Самостоятельно** решаю типовые задачи, изредка гуглю/спрашиваю. |
| **3** | Уверенный   | Решаю **сложные/нестандартные** задачи, оптимизирую, объясняю коллегам. |
| **4** | Эксперт     | **Проектирую** решения, задаю стандарты, менторю; к вам приходят за экспертизой. |

**Пример применения якорей** (навык «Метрики Prometheus/PromQL»):

- **1** — знаю, что такое метрика/лейбл, читаю готовый дашборд.
- **2** — пишу простые запросы (`sum by`, `rate(...)`), нахожу нужную метрику.
- **3** — использую `histogram_quantile`, делаю recording/alerting rules, нахожу
  сатурацию ресурса, настраиваю scrape нового сервиса.
- **4** — проектирую схему метрик сервиса (RED/USE), ревьюю чужие PromQL, задаю
  стандарты именования и кардинальности.

## Маршрут перехода по фазам

| Фаза | Горизонт | Фокус-треки | Критерий готовности |
|------|:--------:|-------------|---------------------|
| **1. Фундамент поверх НТ** | 0–3 мес | Наблюдаемость · Linux и сети | Читаю метрики прод-систем, строю дашборды и осмысленные алерты. |
| **2. Надёжность и автоматизация** | 3–6 мес | SLI/SLO · CI/CD · Python | Определяю SLO и error budget, автоматизирую рутину скриптами. |
| **3. Эксплуатация и масштаб** | 6–12 мес | Контейнеры/K8s · Инцидент-менеджмент | Дежурю, веду постмортемы, деплою и отлаживаю в Kubernetes. |
| **4. Зрелость SRE** | 12+ мес | Распределённые системы · Культура SRE | Проектирую надёжность, системно снижаю toil, менторю. |

> Логика: сначала быстрые победы там, где база НТ уже сильна (наблюдаемость,
> диагностика), затем управление надёжностью и автоматизация, потом эксплуатация
> в масштабе, и в конце — распределённые системы и культура.

## Матрица навыков (самооценка)

Целевой уровень (**Цель**) — ориентир для роли SRE. Колонку **Моя оценка**
заполняйте баллом 0–4.

### 1. Нагрузочное и перформанс-инженерия  ·  *ваш фундамент*

Переиспользуется в SRE для capacity planning и валидации SLO.

| Навык | Инструменты | Примеры прикладных задач | Цель | Моя оценка |
|-------|-------------|--------------------------|:----:|:----------:|
| Моделирование профиля нагрузки | Gatling, анализ прод-трафика, Little's Law | Собрать целевой профиль из прод-метрик (RPS по эндпоинтам); рассчитать число пользователей/интенсивность; обосновать пиковую нагрузку под бизнес-событие | 4 | |
| Инструменты НТ | Gatling (Java), JMeter, k6, Locust | Написать сценарий с feeder-данными и коррелированными токенами; параметризовать профиль (`TARGET_PERCENT`); прогнать в Jenkins и собрать `simulation.log` | 4 | |
| Анализ результатов и bottleneck | Grafana, `simulation.log`, GC-логи, APM | Найти деградацию по p95/p99; связать рост латентности с CPU/GC/пулом соединений; отличить проблему генератора нагрузки от сервера | 4 | |
| Capacity planning | Prometheus, Grafana, расчётные модели | Спрогнозировать число подов на 2× трафика; найти точку насыщения; заложить headroom под пики | 3 | |
| Перформанс-тюнинг (JVM/приложение) | JVM flags, async-profiler, HikariCP, `ulimit` | Подобрать размеры пулов и таймауты; снизить GC-паузы; устранить N+1/блокировки | 3 | |

## Шаблон подсчёта готовности

Для каждого трека: **готовность % = (Σ min(моя оценка, цель) ÷ Σ цель) × 100**
по тем навыкам, которые вы оценили.

| 5. Автоматизация и CI/CD |  | 12 |  | |

| 9. Данные и распределённые системы |  | 10 |  | |

Ориентир интерпретации: **< 40%** — зона активного роста, **40–65%** — в процессе,
**65–90%** — уверенно, **≥ 90%** — можно менторить других.

## Рекомендации по приоритетам для инженера НТ

- **Быстрые победы (используйте текущую экспертизу):** наблюдаемость (Grafana/PromQL
  уже рядом), диагностика Linux/сети (нужна и в НТ), Python/API (у вас есть `ltAuto`).
- **Наибольшая отдача для роли:** SLI/SLO и error budget — именно они превращают
  «инженера по тестам» в SRE, мыслящего надёжностью.
- **Осваивать по мере эксплуатации:** Kubernetes и инцидент-менеджмент — лучше
  всего заходят на реальных дежурствах и разборах.
- **Не гнаться за максимумом:** Go, service mesh, chaos — целевой уровень 2
  (осведомлённость/практика), углублять по потребности команды.

Целевые уровни — рекомендованный ориентир для вашего контура; согласуйте их с
руководителем/командой и при необходимости скорректируйте.
